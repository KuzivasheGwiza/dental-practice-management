# Safe dental demonstration plan

Use **fictional patients**, dates and appointments only. Ask the practice owner to approve any public brand, imagery, or materials.

## Suggested four-minute walkthrough

1. **Business problem:** a patient currently visits reception to arrange and pay for a consultation and receives a return date.
2. **Public website:** show how patients can discover practice services and initiate a booking.
3. **Patient flow:** create a fictional consultation, show booking status and revisit/appointment information and the patient dashboard.
4. **Staff flow:** demonstrate how reception or an administrator views and manages the appointment calendar.
5. **Technical walkthrough:** distinguish the React demo's simulated storage from the Angular / ASP.NET Core / SQL Server application. Explain server-side slot validation and manual API testing with Swagger UI.

## Before publishing

- Strip identifying patient and staff details, payment credentials, medical information, uploaded images and private clinic data.
- Clearly label mock payment screens and synthetic accounts; never advertise a simulated payment as a live transaction.
- Confirm the client's permission to name the practice, display its logo or publish photographs.
- Validate any live payment provider's ability to serve the practice's Zimbabwean merchant/settlement requirements.
- Do not claim measured reductions in queues, no-shows or travel until collected after a real rollout.

The dental product is still under development.
